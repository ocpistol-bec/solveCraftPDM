# Project: SolveCraft PDM
## Enterprise-Grade Product Data Management System for SolveCraft CAD

### 1. Project Objective

Design and implement a complete, self-hosted Product Data Management (PDM) platform integrated with the open-source SolveCraft CAD application.

Source repository:
https://github.com/bherbruck/solvecraft

The long-term objective is to provide functionality comparable to Autodesk Vault Professional, SOLIDWORKS PDM, and the engineering data management capabilities of Fusion 360.

The system must support individual engineers, engineering teams, manufacturers, and organizations operating across multiple locations.

**Primary requirements:**

- Native integration with SolveCraft.
- Rust-first backend architecture.
- Cross-platform desktop compatibility.
- Self-hosted deployment using Docker containers.
- PostgreSQL for relational metadata.
- S3-compatible object storage for CAD files.
- Multi-user access with granular permissions.
- Centralized CAD file management.
- Version and revision control.
- File checkout, check-in, and locking.
- Assembly and component relationship tracking.
- Engineering bills of materials (EBOM).
- Engineering change management (ECR/ECO/ECN).
- Automated STEP, STL, PDF, and drawing generation where supported.
- Browser-based administration and file access.
- Offline-capable CAD workflows.
- REST APIs and event-driven integration.
- Odoo ERP integration.
- AI agent automation through MCP.
- Complete audit trails.
- Horizontal scaling and distributed workers.

The system must be designed for production use, not as a demonstration.

Do not attempt to implement every feature simultaneously. Establish reliable foundations and complete each phase before introducing additional complexity.

### 3. Technology Stack

#### Backend

- Rust, using stable supported toolchains.
- Axum for HTTP APIs.
- Tokio for asynchronous execution.
- SQLx for PostgreSQL access and migrations.
- Serde for serialization.
- UUIDs for internal object identity.
- OpenAPI 3.1 for API documentation.
- Structured tracing and OpenTelemetry.
- Configurable authentication using OpenID Connect.
- Argon2id for any locally managed passwords.

#### Database

PostgreSQL is the authoritative relational database.

Use transactions, foreign keys, unique constraints, optimistic concurrency, and appropriate indexes.

Do not store large CAD binaries directly inside PostgreSQL.

#### File storage

Implement a storage abstraction supporting:

- S3-compatible object storage.
- MinIO or another compatible self-hosted implementation.
- Local filesystem storage for development.
- Network-backed storage through the object-storage service.

Files must be content-addressed using SHA-256.

Uploaded objects must be immutable once committed.

#### Frontend

Use a modern TypeScript frontend with React or another well-supported framework for the PDM web portal.

The CAD application itself must retain its existing Rust/egui architecture.

Do not rewrite the SolveCraft desktop interface.

#### Deployment

Provide:

- Dockerfiles.
- Docker Compose.
- Docker Swarm-compatible deployment examples.
- Environment-based configuration.
- Health and readiness endpoints.
- Database migration tooling.
- Persistent volume definitions.
- Backup and restore scripts.
- TLS reverse-proxy examples.

All services must be deployable independently of the engineer's workstation.

### 6. File Versioning and Revision Management

Implement two distinct concepts.

#### File versions

A new file version is created whenever an engineer successfully checks in modified content.

Example:

- Version 1
- Version 2
- Version 3
- Version 4

Every committed version is immutable.

Each version records:

- Unique identifier.
- Parent version or lineage.
- Author.
- Timestamp.
- Commit message.
- Content hash.
- File size.
- Native file format version.
- Associated dependencies.
- Extracted metadata.

#### Engineering revisions

Engineering revisions represent controlled design releases.

Example:

- Revision A
- Revision B
- Revision C

Multiple working file versions may exist before a revision is released.

Released revisions must reference immutable, approved file versions.

Support configurable revision schemes, including alphabetic and numeric schemes.

Never silently replace or mutate a released revision.

Allow previous versions to be retrieved and restored by creating a new working version.

Implement revision comparisons, initially for metadata, file references, BOMs, and geometry measurements.

Later extend comparisons to graphical model differences.

### 7. Checkout, Check-in, and Locking

Implement exclusive checkout as the default policy for native CAD files.

Required operations:

- Checkout.
- Check-in.
- Undo checkout.
- Refresh local copy.
- Get latest.
- View lock owner.
- Request lock release.
- Administrative lock override.

Checkout must record:

- User.
- Workstation.
- File.
- Base version.
- Checkout time.
- Lease or lock status.

Use atomic server-side operations to prevent simultaneous conflicting checkouts.

A check-in must verify:

1. User permissions.
2. Valid checkout ownership.
3. Expected base version.
4. File integrity.
5. Dependency validity.
6. Required metadata.
7. Workflow restrictions.

Do not allow a stale client to overwrite newer server content.

Support configurable lock leases and recovery from crashed clients.

Offline edits must remain local until synchronization. If the server version has changed, detect the conflict and require an explicit resolution.

### 9. CAD File References and Assemblies

This is a critical architectural requirement.

Implement stable references between parts and assemblies.

Each reference must contain:

- Referenced document identity.
- Referenced version or revision policy.
- Component identity.
- Occurrence identity.
- Assembly transform.
- Suppression state.
- Quantity or occurrence count.
- Resolution status.

Support:

- Parts used in multiple assemblies.
- Nested subassemblies.
- Repeated components.
- Missing-reference detection.
- Circular-reference detection.
- Reference replacement.
- Reference update.
- Where-used searches.
- Dependency graphs.
- Recursive BOM generation.

Do not rely on absolute filesystem paths for managed references.

Introduce a vault URI scheme, such as:

`pdm://organization/project/document-id`

Keep the stable identity separate from the requested version or revision.

Define how floating references are resolved and frozen into immutable release manifests.

When opening a managed assembly, resolve all required references consistently.

If SolveCraft lacks a required native assembly capability, implement the necessary CAD-side foundation before claiming full assembly support.

### 12. Lifecycle Management

Implement configurable lifecycle workflows.

Default states:

`Work in Progress → In Review → Approved → Released → Obsolete`

Support additional states and organization-specific transitions.

Lifecycle transitions must enforce:

- Role permissions.
- Required properties.
- Required approvals.
- Valid reference resolution.
- Required generated artifacts.
- BOM validation.
- Revision assignment.
- Audit recording.

Released content must be immutable.

A change to a released design must create a new working lineage and eventually a new revision.

Prevent unapproved or obsolete components from entering a released assembly unless explicitly permitted by policy.

- Reason.
- Requester.

- Affected parts.

- Impacted assemblies.

- Effective date.
- Status.

### 26. Multi-Agent Development Structure

Use specialized coding agents with clearly separated ownership.

**Agent 1 — Technical Architect**
Owns architecture, API contracts, shared interfaces, dependency rules, and design decisions.

**Agent 2 — Database Engineer**
Owns PostgreSQL schema, migrations, indexing, transactions, and integrity constraints.

**Agent 3 — Backend Engineer**
Owns Rust API modules, authentication, permissions, workflows, and audit events.

**Agent 4 — Storage Engineer**
Owns immutable blobs, uploads, downloads, integrity verification, and retention.

**Agent 5 — CAD Integration Engineer**
Owns SolveCraft integration, native commands, document identity, and workspace support.

**Agent 6 — Assembly/BOM Engineer**
Owns reference graphs, assembly occurrences, BOM generation, and where-used logic.

**Agent 7 — Frontend Engineer**
Owns the web portal, administration, file browser, search, and workflow UI.

**Agent 8 — Integration Engineer**
Owns Odoo synchronization, MCP, background workers, and external API integrations.

**Agent 9 — QA/DevOps Engineer**
Owns CI, containers, integration tests, performance tests, and recovery validation.

Agents must not independently modify shared contracts without architect review.

Use small, reviewable changes with tests.

Parallelize independent modules, not tightly coupled database and API changes.

### 27. Development Rules

1. Do not rewrite SolveCraft from scratch.
2. Do not remove existing CAD functionality.
3. Preserve compatibility with unmanaged local files.
4. Use Rust for core backend services.
5. Prefer simple, testable architecture.
6. Avoid unnecessary microservices.
7. Never overwrite immutable versions.
8. Never bypass authorization checks.
9. Never assume a CAD feature exists without verifying it.
10. Maintain database migrations.
11. Maintain automated tests.
12. Document architectural decisions.
13. Implement structured error handling.
14. Use explicit transactions for critical operations.
15. Keep business rules outside UI code.
16. Keep integration adapters separate from core domain logic.
17. Avoid introducing unreviewed licensing dependencies.
18. Maintain a working build after every phase.
19. Track incomplete features explicitly.
20. Never report a feature as complete without passing its acceptance tests.
